1. 工具超时如何处理？

区分未执行、执行中、执行成功但响应丢失。读操作可按错误类型重试；写操作需先查业务结果或使用幂等键。设置连接超时、调用超时和整个任务截止时间，避免某次工具吞掉全部预算。

退避要带随机抖动，限制重试次数。参数错误与权限错误通常不应重试；限流和暂时性网络故障才可能受益。

2. 如何保证不重复下单？

为业务动作生成稳定幂等键，在数据库唯一约束或外部 API 的幂等机制下存储执行结果。重试同一动作返回同一结果。不能每次重试生成新键，也不能把模型生成的自然语言描述当作可靠业务主键。

“恰好一次”要说明作用范围。消息消费和网络调用可能至少一次，系统依靠去重、事务及结果查询实现业务上的单次效果。

3. Checkpoint 是否等于事务？

不是。图状态已保存与外部付款已完成是两个系统的状态。节点在付款后、保存状态前崩溃，恢复可能重复调用。需要幂等、状态机、补偿或可靠消息机制协调，不能仅依赖框架恢复功能。

4. HITL 审批如何落地？

在敏感动作前暂停，保存线程状态，展示具体参数和影响。审批结果绑定动作及版本，恢复时重新验证权限和资源状态。参数发生变化需重新审批，避免批准的是 A，执行的是 B。官方 HITL 指南

5. Prompt injection 如何防御？

将网页、文档、工具输出视为不可信数据，不能让其中指令重定义系统权限。策略在应用与工具层实施：最小工具集、服务端鉴权、隔离执行、出站限制和敏感动作审批。仅增加一句“忽略恶意提示”不能建立安全边界。

测试覆盖文档中的伪系统指令、要求泄露凭证、修改工具参数和污染长期记忆等。观察是否发生未经授权的实际动作，比看模型是否口头拒绝更重要。

6. 工具权限如何划分？

按读写、资源范围和动作风险设计。凭证由运行时注入，模型不应看到明文密钥。订单查询与退款拆开，文件读与 shell 执行分开，开发环境和生产环境分开。每次调用重新验证资源归属。

7. 为什么路径限制不等于沙箱？

文件工具的路径解析只能限制该工具的文件访问。若同时允许宿主 shell，命令可能访问其它位置、网络和进程。真正的执行隔离还包括容器或虚拟化边界、资源限额、网络策略和凭证隔离。

8. Agent 评估为什么不能只看最终答案？

答案可能碰巧正确，但轨迹包含越权读取、重复写入或过多调用。分层看任务结果、工具选择、参数正确性、证据忠实性、副作用、成本和延迟。既有端到端集，也有局部单元测试。

严格要求每次工具顺序完全一致也可能误判：不同有效路径都能成功。评估应约束必要条件与禁止动作，而不是机械复制一条参考轨迹。

9. LLM-as-judge 有什么局限？

会受提示词、答案顺序、文本长度和评判模型偏好影响。用明确 rubric、匿名随机排序、人工校准和重复抽样；关键业务规则优先确定性断言。评判模型与被测模型共享偏差时尤其要注意。

10. 指标怎么定义？

指标 定义注意点
任务成功率 预定义验收条件，不按自称完成计数
工具成功率 区分传输成功、业务成功、语义正确
接管率 说明哪些任务允许人工辅助
p50 / p95 延迟 固定负载、任务分布和统计窗口
单位成功任务成本 总支出除以成功任务数，包含失败和重试
越权动作次数 记录真实执行与被拦截尝试，分开统计

不要只报平均 token 下降：可能同时降低成功率。收益应在相同任务集与验收标准下比较。

11. 如何降低成本和延迟？

先看 trace 找主要耗时：检索、排队、首 token、模型生成、工具或重试。减少无关上下文，缓存稳定结果，按复杂度路由模型，合并冗余工具请求，对独立 I/O 并发，并设置预算。

缓存键需包含权限、参数、数据版本和必要的模型配置。过期或跨用户缓存命中可能比慢更严重。小模型替换后要重新测任务质量。

12. 流式输出有哪些工程坑？

文本可能先到但工具还没完成；用户断开连接不代表后端动作自动取消；中途失败需区分已执行副作用与未完成显示。事件应带 run_id、序号和类型，支持前端去重与重连。

涉及最终结论或交易状态时，不把尚未验证的片段呈现为已完成结果。取消应传播到可取消调用，并保留审计记录。

13. 线上日志应记录什么？

记录版本、run/thread ID、工具输入摘要与结果状态、token、耗时、检索文档 ID、记忆读写和人工干预。对敏感内容脱敏，区分业务日志和调试 trace 的权限与保留期。

不需要记录隐藏思维链。用可观察动作、结构化决策字段和实际证据定位问题。

14. 如何灰度和回滚？

模型、prompt、工具 schema、知识索引和依赖包都应版本化。先离线回归，再小流量灰度，比较成功率、错误类别与成本。为有副作用任务提供受控测试环境或只读回放。

回滚应用版本时还要考虑 checkpoint 和存储 schema 的兼容性；旧图不一定能直接读取新状态。保留迁移和降级策略。

15. 并发如何控制？

按用户、租户、供应商和全局分别限流。独立查询可并行，依赖结果或修改同一资源的动作需排序、锁或版本控制。共享 store 中的读改写不是天然原子操作。

面对 429 或积压，使用队列、背压、超时和降级，不让 Agent 无限重试放大故障。
