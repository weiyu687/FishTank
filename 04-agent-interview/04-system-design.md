# Agent 应用开发面试 04：系统设计与项目追问

[TOC]

## 1. 企业知识问答 Agent 怎么设计？

先确认用户、文档规模、更新频率、权限粒度、回答时延和无答案策略。基础链路：鉴权 → 查询理解 → 权限内检索 → 重排 → 证据组织 → 回答与引用校验。复杂问题才增加多轮检索。

离线管道保留文档版本与权限；线上 trace 记录召回 ID。评估集包含答案明确、需多文档组合、没有答案、冲突版本和无权限文档。上线监控引用错误和拒答分布。

追问：部门权限刚变化怎么办？权限读取不能只依赖 长期缓存；文档检索与原文读取均需重新验证，相关缓存应失效。先保证权限正确，再谈命中率。

## 2. 订单客服 Agent 怎么设计？

把知识回答、订单查询、修改动作拆开。模型负责理解意图与收集缺失信息；业务服务验证订单归属、状态与规则。退款动作使用幂等键、审批和审计，成功后查询最终状态再回复。

失败场景：订单不存在、已退款、支付服务超时、用户撤销、审批后订单状态改变。每种状态需要可恢复路径，不能统一返回“请稍后重试”。

追问：退款成功但回复失败？用户再次请求时用同一业务操作标识查询原结果，不再次退款。通信重试与业务重试要分开。

## 3. 研究报告 Agent 怎么设计？

先把问题拆为可检索子问题，每条结论绑定来源、日期和原文片段。独立来源可以并行调查，汇总阶段处理冲突并标明未知。最终检查引用是否支持主张、资料是否过时、是否把推断写成事实。

预算按来源数量、工具次数、token 和总时长限制。对没有足够证据的问题提前停止，不通过不断重试制造更多重复内容。

## 4. 带个人记忆的学习助手怎么设计？

将稳定偏好、学习进度和知识掌握度分开。偏好由明确用户反馈更新；进度来自实际完成记录；掌握度是带置信度的估计，不能当成用户事实。每项信息保留来源与时间。

存储按租户与用户隔离，允许查看、更正和删除。评估关注新会话是否正确延续、过期记录是否被纠正以及是否泄露其它用户内容。实现参见 [记忆实验](../02-langchain/deepagents/02-memory-lab.md)。

## 5. 代码 Agent 怎么设计？

使用独立工作目录与受控执行环境，工具覆盖读文件、定位、编辑、运行测试与查看 diff。任务验收包括行为测试、变更范围和产物，而不仅是代码能生成。

网络和凭证最小化；依赖安装、长进程和资源消耗有边界。检查失败后根据具体证据修复，不把每次失败都交给同一条泛化提示。提交前确保无测试产物和密钥混入。

## 6. 面试如何讲项目而不空泛？

按“场景与基线 → 最难问题 → 方案与取舍 → 验证 → 局限”展开。明确自己负责的组件、实际数据规模、任务分布和指标口径。没有做过的优化明确说是下一步设计，不编造生产成果。

示例结构：原流程需要人工检索多个资料源；先搭固定 RAG 作为基线；发现跨文档问题召回不足；引入受限多轮检索；用同一批问题比较成功率和单位成功成本；记录仍然失败的冲突政策案例。

## 7. 高频项目追问清单

|追问|回答需要的证据|
|---|---|
|为什么选择这个框架？|需求映射、替代方案与维护成本|
|为什么不是固定工作流？|需要动态决策的具体任务|
|你最大的失败案例？|真实输入、trace、根因、修复与回归|
|提高了多少准确率？|评测集规模、口径、基线与置信范围|
|如何证明记忆有效？|新线程、新进程、随机标记和隔离测试|
|如何控制成本？|调用分布、重试占比和成功任务成本|
|能承受多少并发？|负载条件、限流、p95 和瓶颈|
|工具重复执行怎么办？|业务幂等与结果确认机制|
|模型更换会怎样？|回归集、工具调用兼容与灰度方案|
|知识删除后还会回答吗？|索引、缓存、摘要和备份处理|

## 8. 现场设计题的答题顺序

1. 确认需求与约束，明确什么算成功。
2. 给出最简单可用基线。
3. 画数据流与权限边界。
4. 解释状态、记忆和持久化。
5. 设计工具契约及失败恢复。
6. 给出评估、可观测性和发布方案。
7. 说明性能瓶颈、成本与下一步取舍。

不要一开始罗列向量库、框架和模型名称。架构图中的每个组件都应对应一个需求或失败模式。

## 10. 综合模拟题

“设计一个为企业员工查询制度、记住个人偏好并代提工单的 Agent。”回答时至少覆盖：文档权限、知识更新、记忆隔离、工单幂等、人工确认、状态恢复、无答案策略和评测。

自评标准：概念解释清楚只能算基础；能讲失败路径算具备工程意识；能拿出实验、trace、指标和取舍才说明真正完成过验证。
